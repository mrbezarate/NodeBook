# ADR-001: Core Freeze v1.0 Architectural Decisions

**Статус:** Принято (Core Freeze v1.0)  
**Дата:** 31 Июля 2026 г.

Этот документ фиксирует фундаментальные архитектурные решения ядра системы Brain. Цель документа — объяснить **почему** система построена именно так, чтобы предотвратить случайное разрушение инвариантов при попытках "упростить" архитектуру в будущем.

---

## 1. Event Sourcing вместо CRUD (прямого обновления Entity)

* **Проблема:** При традиционном CRUD-подходе исходный текст сообщения от пользователя теряется после извлечения из него фактов. Если модель (LLM) ошибается, или если мы обновляем логику извлечения, старые данные невозможно переобработать.
* **Рассмотренные альтернативы:** Прямое редактирование `Entity` после каждого сообщения (типичный RAG или Notetaking).
* **Почему были отклонены:** Необратимая потеря контекста. При изменении промпта или схемы базы данных пришлось бы вручную исправлять сотни заметок.
* **Окончательное решение:** Внедрить Event Sourcing. Всё начинается с неизменяемого `RawEvent`.
* **Последствия:** 
  * *Плюсы:* 100% защита от потери данных. Возможность переобработать всю историю при смене алгоритма.
  * *Минусы:* Увеличение объёма хранилища; необходимость строить механизм Projection.

## 2. Projection как одноразовый кэш

* **Проблема:** Как хранить агрегированные сущности (`Entity`), если источником правды являются события?
* **Рассмотренные альтернативы:** Хранить `Entity` как источник правды, а события использовать просто как логи.
* **Почему были отклонены:** Рассинхронизация. Если кто-то отредактирует `Entity` напрямую, она перестанет соответствовать событиям, что сломает механизм Rebuild (переобработки).
* **Окончательное решение:** `Source of Truth = Raw Events + Observations`. Таблица `entities` (Projection) считается одноразовым кэшем.
* **Последствия:**
  * *Плюсы:* В любой момент можно выполнить `DROP TABLE entities` и пересобрать её из событий без единой потери знаний.
  * *Минусы:* Нельзя разрешать пользователю (или коду) редактировать `Entity` напрямую в обход пайплайна.

## 3. LLM строго отделена от детерминированной логики

* **Проблема:** LLM склонны к галлюцинациям, нестабильности форматов и недетерминированному поведению. Если поручить LLM принимать архитектурные решения (слияние заметок, генерация ID), система станет хрупкой.
* **Рассмотренные альтернативы:** Использовать LLM как "оркестратор" (Agent), который сам ходит в базу, сам ищет дубликаты и сам решает, как их обновить.
* **Почему были отклонены:** Невозможность гарантировать консистентность БД. Ошибки Chain-of-Thought (CoT) приводили к поломке пайплайна. Невозможность нормально тестировать систему.
* **Окончательное решение:** LLM выполняет роль "тупого" Extractor'а. Она только извлекает JSON-факты из текста.
* **Последствия:**
  * *Плюсы:* Генерация UUID, нормализация имён, агрегация Markdown и транзакции SQLite остаются в строгом, типизированном и быстром Rust-коде.
  * *Минусы:* Требуется писать больше кода для связывания (Identity Resolver).

## 4. Identity Resolution выполняется строго после Extractor'а

* **Проблема:** На каком этапе мы должны понимать, относится ли сообщение к существующему проекту/сущности или к новому?
* **Рассмотренные альтернативы:** Передавать всю базу существующих сущностей прямо в промпт Extractor'а.
* **Почему были отклонены:** Ограничение контекстного окна. Когда сущностей станет 10 000, промпт лопнет, а LLM запутается и будет галлюцинировать.
* **Окончательное решение:** Сначала Extractor выделяет сырые имена из текста в вакууме. Затем IdentityResolver (отдельный Rust-компонент) прогоняет их через каскад: Exact -> Alias -> Fuzzy (Jaro-Winkler) -> Semantic (LLM fallback для маленького списка кандидатов).
* **Последствия:**
  * *Плюсы:* Независимость от размера базы знаний. Высокая скорость резолва.
  * *Минусы:* Сложный многоступенчатый каскад `CascadedIdentityResolver`.

## 5. Job Queue отделена от Raw Events

* **Проблема:** Обработка LLM может занимать 5-15 секунд, а API Telegram требует ответа мгновенно. 
* **Рассмотренные альтернативы:** Делать весь пайплайн синхронно прямо в обработчике команды `/message`.
* **Почему были отклонены:** Блокировка UI, таймауты Telegram, потеря сообщений при падении бота во время генерации ответа LLM.
* **Окончательное решение:** Telegram только пишет `RawEvent` и связанный `Job` со статусом `pending`. Отдельный фоновый воркер асинхронно выбирает задачи через атомарный `UPDATE ... RETURNING`.
* **Последствия:**
  * *Плюсы:* Идеальная отзывчивость бота. Crash Recovery (сообщение не потеряется при рестарте). Возможность горизонтального масштабирования воркеров.
  * *Минусы:* Асинхронная природа (пользователь получает финальный результат не сразу).

## 6. Ядро (`brain-core`) ничего не знает о Telegram

* **Проблема:** Бот в Telegram получает специфичные типы данных (chat_id, message_id). Легко начать прокидывать их прямо в ядро для отправки ответов.
* **Рассмотренные альтернативы:** Смешать обработчики команд и логику извлечения.
* **Почему были отклонены:** Нарушение SRP (Single Responsibility Principle). Невозможность переиспользовать ядро в CLI или расширении для браузера. Утечка HTML/Markdown форматирования в базу данных.
* **Окончательное решение:** Строгое разделение. Telegram-бот (`apps/telegram-bot`) — это просто адаптер, который конвертирует сообщения в `RawEvent` и вызывает методы `BrainEngine`.
* **Последствия:**
  * *Плюсы:* Легкость тестирования (можно тестировать ядро без Telegram API). Переносимость архитектуры.
  * *Минусы:* Небольшой оверхед на конвертацию DTO.

## 7. Единый Pipeline для всех источников

* **Проблема:** Со временем появятся новые источники: Voice (аудио), Email, Web Clipper.
* **Рассмотренные альтернативы:** Писать для каждого источника свою логику сохранения в БД.
* **Почему были отклонены:** "Расползание" архитектуры, дублирование кода, потеря инвариантов системы.
* **Окончательное решение:** Любой источник обязан конвертироваться в `RawEvent` и вставать в общую очередь `Job Queue`. Вся дальнейшая бизнес-логика (`Consolidator` -> `Extractor` -> `Identity` -> `Observation` -> `Projection`) едина.
* **Последствия:**
  * *Плюсы:* Централизованный контроль качества, предсказуемость, единое место для оптимизации.
  * *Минусы:* Необходимость приводить все типы данных к текстовому представлению `RawEvent.text` перед обработкой.

## 8. Возможность полностью пересчитать систему из истории

* **Проблема:** Алгоритмы `Extractor` и `IdentityResolver` будут неизбежно улучшаться (v1 -> v2). Как обновить старые данные?
* **Рассмотренные альтернативы:** Использовать миграции БД или писать одноразовые скрипты трансформации данных.
* **Почему были отклонены:** Ненадёжно, чревато ошибками, не решает проблему кардинальной смены логики выделения фактов.
* **Окончательное решение:** Механизм `rebuild`. Удаляются только производные `Observations`, статус `Job` откатывается к `pending`, и пайплайн отрабатывает заново с новым Extractor'ом.
* **Последствия:**
  * *Плюсы:* Истинная Time-Machine архитектура. Качество базы знаний улучшается ретроспективно.
  * *Минусы:* При перестроении (Rebuild) 10 000 сообщений потребуется много токенов и времени LLM. Требуется сохранять метрики версионирования схемы и промпта (`schema_version`, `extractor_version`).

## Архитектурные инварианты (Architectural Invariants)

Эти правила не подлежат обсуждению при добавлении новых функций. Их нарушение означает разрушение архитектуры.

1. **Никто никогда не изменяет RawEvent после записи.** Любая корректировка знаний создаёт новые производные данные, но история событий остаётся неизменной (Append-only).
2. **Observation — производная сущность.** Её можно безопасно удалить и восстановить повторной обработкой RawEvent через Extractor.
3. **Entity — исключительно Projection.** Она не является Source of Truth. Если сделать `DROP TABLE entities`, система обязана полностью восстановить её из `RawEvents` + `Observations`.
4. **LLM не принимает архитектурных решений.** Модель не генерирует UUID, не объединяет сущности напрямую, не пишет SQL и не определяет жизненный цикл объектов. Она работает как чистая функция: `Текст -> Структурированные Факты`.
5. **Любой новый источник обязан использовать единый Pipeline.** Запрещено создавать обходные пути обработки для "новых клиентов" (Voice, Browser Extension, GitHub).
6. **Воспроизводимость состояния.** При наличии истории событий и одинаковой версии Extractor система обязана получить идентичный результат после полного Rebuild.

---

## Антицели (Non-goals)

Что система принципиально **не пытается** делать:

* Brain **не** является автономным AI-агентом (выполняющим действия от лица пользователя).
* Brain **не** принимает решения за пользователя.
* Brain **не** сохраняет рассуждения (Chain-of-Thought) моделей в базу данных.
* Brain **не** позволяет LLM генерировать SQL или напрямую мутировать состояние БД.
* Brain **не** зависит от конкретного провайдера LLM (Ollama, OpenAI, Anthropic — взаимозаменяемы).
* Brain **не** использует векторную базу данных как источник истины (только как индекс).

---

## Операционные гарантии (Operational Guarantees)

Контракт надёжности, который система обязуется выполнять в production-режиме:

* **At-least-once обработка событий.** Ни одно сообщение Telegram не будет потеряно.
* **Идемпотентность повторной обработки.** Воркер может упасть и перезапуститься на одном и том же `Job` без дублирования сущностей.
* **Crash Recovery.** Перезапуск процесса посреди обработки оставляет систему в консистентном состоянии.
* **Детерминированный Rebuild.** Гарантированная возможность перестроить всю базу с нуля командой `/rebuild`.
* **Версионирование логики.** Каждое Observation привязано к версии схемы и версии промпта Extractor'а.
* **Аудируемость.** Любое состояние сущности можно отследить до исходного сообщения через команду `/debug`.

---

## Правило эскалации архитектуры

> **Если новая функция не может быть реализована без нарушения Architectural Invariants, значит нужно менять архитектуру через новый ADR, а не обходить ограничения локальными костылями.**

Это правило запрещает "быстрые грязные фиксы" ядра. Любое изменение инвариантов должно обсуждаться и фиксироваться в ADR-002, ADR-003 и т.д.

---

## Философия платформы

С момента заморозки `brain-core` больше не является "кодом бота". Это — **Платформа обработки знаний**. 
Telegram, CLI, Browser Extension, REST API — это лишь тонкие клиенты (адаптеры) над этой платформой.

Критерий оценки любого будущего изменения:
> **«Улучшает ли это платформу целиком или решает проблему только одного клиента?»**

Если изменение нужно только для Telegram (например, форматирование кнопок или парсинг стикеров) — оно пишется в `apps/telegram-bot`. Если оно улучшает извлечение фактов из любого текста — оно идёт в `brain-core`.

## Definition of Done (Core Freeze)

Объективные критерии, по которым система проходит аудит на соответствие архитектуре Core Freeze v1.0. Если любой из пунктов не выполняется, архитектура нарушена:

1. **Единый конвейер:** Все источники данных без исключения создают `RawEvent` и используют единый пайплайн.
2. **Восстановимость:** Любую Entity можно на 100% восстановить из истории событий.
3. **Автоматический Rebuild:** Полный пересчёт базы (Rebuild) проходит без ручного вмешательства.
4. **Версионирование извлечения:** Все изменения Extractor сопровождаются новой версией промпта, а старые данные могут быть переобработаны.
5. **Data-Driven Quality:** Для каждого исправленного бага в алгоритме существует Fixture и регрессионный тест (TDD).
6. **Агностика ядра:** `brain-core` компилируется и работает без зависимостей от Telegram, Discord, CLI или любого другого интерфейса.
7. **Traceability:** Любой сбой можно расследовать через `/debug` вплоть до исходного сырого текста.
8. **Идемпотентность:** Повторная обработка одного и того же события никогда не создаёт дубликатов в Projection.
